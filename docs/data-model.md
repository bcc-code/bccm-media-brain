# Data model in use

The full schema is in `internal/db/migrations/` (about 40 tables). This page covers the part that
has code on top of it and why it is shaped this way. Ids are prefixed, time-ordered text ids
(`AS-...` asset, `FI-...` file, ...), generated by the database.

```
program 1--n project n--m asset 1--n asset_version 1--n rendition n--m file 1--n file_copy --1 storage_location
                                                          |                 1--n file_hash
                                                          1--n subtitle_track 1--n subtitle_cue
```

## Users and service accounts

`app_user.kind` is `person` or `service`. A service account is a machine client: the same row as
a user, so grants, groups and `created_by` columns need nothing extra. Its `external_id` is
`service|<name>` and it has no email. `service_token` (`TK-...`) holds its credentials: the
SHA-256 of each token (never the token), a name, who created it, when it expires, when it was
last used and when it was revoked. See [security.md](security.md#machine-clients).

An email belongs to one account whatever its case: the unique index is on `lower(email)`, the
same expression the lookup by email uses, so `Ann@x.org` and `ann@x.org` cannot both exist and
the lookup does not scan the table.

## Programs and projects

A **program** is a series or production (`JOSH`); a **project** is one unit of work in it
(`JOSH_S01_E03`). The project code must start with the program code; the database checks the
format and the service checks the prefix. A program with projects cannot be deleted.

## Assets

An **asset** is the logical item: one camera clip, one finished programme. It is linked to
projects with a role (source, deliverable, reference) and can be in several.

- **asset_version**: ordered edits of the asset (rough cut, review, final). The number is
  assigned by the database as max + 1.
- **rendition**: one concrete form of a version: the master, an encode, a dub, subtitles.
- **rendition_file**: the files that make up a rendition, with a role and position.

Why three levels: the same edit exists in many forms (languages, encodes), and a new edit
replaces all of them together.

**revision** (program, project, asset, asset_version, rendition, storage_location): starts at 1
and goes up by one with every UPDATE of the row, counted by a trigger so that no statement can
forget it. The same six tables have `updated_at`.
Links, grants and children do not move it. An update can name the revision it was based on and
is refused when the row has moved on ([api.md](api.md)). It has nothing to do with
`asset_version.number` (which edit of the asset) or a subtitle track's `revision` (which
rewrite of the cues).

Deleting an asset removes its versions, renditions and subtitles, **never its files**. An asset
used in a timeline cannot be deleted.

## Files

A **file** is unique content, identified by its **hashes**, not by a path. The same content found
in three places is one file with three **copies** (storage location + relative path).

- Files are **registered from metadata** the caller supplies (size, codec, probe output, hashes,
  copies). MediaBrain does not read disks, hash or probe yet; an ingest tool does that and calls
  `registerFile`.
- Registering content whose hash is already known returns the existing file and adds any new
  hashes and copies, so ingest can be re-run safely. Hashes that point at two different files, a
  different size for a known hash, or a path that already holds another file are conflicts.
- Hash algorithms: xxh3_128, blake3, sha256, md5, and sha1 because that is what Vidispine
  records for the files imported from Vidispine.
- A copy has a status: present, missing, mismatch (hash no longer matches).
- A file with copies, or used by a rendition, cannot be deleted.

## Imported from Vidispine

An asset imported from Vidispine carries the item id in `legacy_ids` and Vidispine's fields under
`metadata.vidispine` (`itemId`, `refreshedAt`, `fields`). Its original file hangs on a version
labelled "Vidispine original", and the copy lies on a storage location named after the Vidispine
storage. Refresh replaces `metadata.vidispine` only. See [vidispine.md](vidispine.md).

## Subtitles

A **subtitle_track** is one revision of the subtitles of one rendition. Tracks are never changed:
every import and every edit writes a **new revision** that points at its parent, so history and
"who changed what" come for free.

- The schema allows one revision chain per rendition, so **each language gets its own `subtitle`
  rendition** on the version, created on first import.
- Only the latest revision can be edited. An edit based on an older one is a conflict, which
  stops two editors from silently overwriting each other.
- Cues store start/end in milliseconds, text and an optional speaker. Import reads SRT and
  WebVTT; export writes both (SRT has no place for the speaker, so it is dropped).
- `asset_id` on tracks and cues is a copy kept for permission filtering and later search.

## Reference data

`asset_type` and `language` are seeded by migrations and read-only through the API. Dev-data
reset keeps them.

## Not built yet

Tags, credits, rights, asset groups, notes, collections, saved searches, timelines, faces, cue
search and embeddings exist as tables only.
